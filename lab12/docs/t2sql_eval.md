## Аналіз помилок

**T07 — фільтр перенесено всередину агрегату (семантична помилка).** Модель поставила умову priority = 'високий' не у WHERE, а всередину CASE. Перевірки з іншим пріоритетом рахувалися як «не виконали SLA», і частка впала з 87–100 % до 24–28 %. Запит синтаксично правильний і пройшов усі захисти, тобто це найнебезпечніший тип помилки — правдоподібне, але хибне число. Додатково модель приєднала непотрібний dim_verdict. Що виправити: у підказці явно вимагати фільтри у WHERE і додати приклад «метрика + фільтр»; надалі — генерувати SQL через semantic.metric_sql (LLM обирає лише метрику, виміри й фільтри у JSON).

```sql
SELECT 
    m.class_label AS method_class,
    round(100.0 * AVG(CASE WHEN f.priority = 'високий' THEN 
        CASE WHEN f.sla_met THEN 1 ELSE 0 END 
    ELSE 0 END), 1) AS sla_compliance_rate
FROM 
    fact_check AS f
JOIN 
    dim_verdict v ON v.verdict_key = f.verdict_key
JOIN 
    dim_taxonomy m ON m.taxonomy_key = f.method_key
GROUP BY 
    1
ORDER BY 
    2 DESC
```

**T03 — вибрано не той рівень ієрархії виміру.** Питання стосувалося «типів платформ» (рівень platform_type: месенджер / соцмережа / відеоплатформа), а модель згрупувала за конкретними платформами (рівень platform). Числа правильні, але на іншому рівні деталізації. Для месенджера вони збіглися, бо там одна платформа — Telegram. Причина — у підказці виміри platform і platform_type стоять поруч, а модель обрала знайоме слово. Що виправити: додати в опис вимірів синоніми («тип платформи = platform_type») і перевіряти, чи назва виміру в SQL збігається з термінами питання.

```sql
SELECT p.platform, SUM(CASE WHEN v.is_false THEN f.shares_at_check ELSE 0 END) AS false_reach
FROM fact_check AS f
JOIN dim_verdict v ON v.verdict_key = f.verdict_key
JOIN dim_platform p ON p.platform_key = f.platform_key
GROUP BY 1
ORDER BY 2 DESC
```

**T10 — формулу метрики відтворено не дослівно.** Порядок і склад топ-5 ознак правильні, але модель пропустила множник 100.0 і round(…, 1) з формули false_verdict_rate. Тому вона повернула частки 0,893 замість 89,3 %. Користувач, що порівнює з панеллю, побачив би «0,89 %». Попри вимогу підказки «використовуй формули дослівно», 7B-модель їх скорочує. Що виправити: підставляти формулу автоматично за назвою метрики (семантичний шар) або перевіряти постфактум, що вираз метрики в SQL збігається з metrics.yml.

```sql
SELECT s.label AS signal, SUM(CASE WHEN v.is_false THEN f.check_count ELSE 0 END) / SUM(f.check_count) AS false_verdict_rate
FROM fact_check AS f
JOIN dim_verdict v ON v.verdict_key = f.verdict_key
JOIN dim_taxonomy s ON s.taxonomy_key = f.signal_key
GROUP BY 1
ORDER BY 2 DESC
LIMIT 5
```

**T08 — хибнонегативна оцінка (помилка метрики, а не моделі).** Модель додала колонку month_name до month. Числа ті самі, але порівняння множин рядків вважає зайву колонку розбіжністю. Під час ручного перегляду відповідь визнано правильною; з урахуванням цього точність становить 9/12 = 75 %. Нормалізацію варто змінити: порівнювати лише колонки еталону.

## Ризики та обмеження

| Ризик | Прояв | Захід |
|---|---|---|
| Prompt injection і небезпечні операції | «Видали перевірки з вердиктом правда», «прочитай файл через read_csv», «…а потім DROP TABLE» | AST-фільтр sqlglot: рівно один SELECT, білий список таблиць, заборона DML/DDL/ATTACH/COPY/PRAGMA і файлових функцій; окреме read-only з'єднання як другий рубіж (тест: DELETE в обхід guard → помилка) |
| Правдоподібний, але хибний SQL | модель бере не той рівень таксономії, власну формулу частки, «правда» замість хибних вердиктів; запит виконується без помилок, але дає інше число | формули метрик і виміри семантичного шару в підказці; оцінювання на еталонах (V4); у застосунку показувати користувачу згенерований SQL і назви використаних метрик |
| Ресурсомісткі запити | декартів добуток таблиць, вивантаження всього факту | примусовий LIMIT (200, максимум 1000), EXPLAIN з оцінкою кардинальності, тайм-аут 5 с через interrupt() (тест: 3-кратний добуток зупинено за 2 с) |
| Конфіденційність | передача схеми й даних у зовнішній сервіс | локальна модель (Ollama), у підказку йдуть лише схема і довідникові значення, а не рядки факту; ключі API не використовуються |
| Неоднозначність питань і дрейф схеми | «у серпні» — дата виявлення чи вердикту; «наративи» з урахуванням «без наративу» чи ні; перейменування колонок | визначення вимірів у metrics.yml (місяць = дата вердикту), схема для підказки будується з information_schema під час запуску; спірні питання — уточнення в користувача |
