# Рекомендаційний модуль Hub (ЛР16, Р1)

## Мета і користувачі

Аналітик фактчекінгу щодня переглядає десятки фрагментів довідкових і внутрішніх документів Hub: статті про пропаганду, методики перевірки фото, регламенти вердиктів, досьє наративів. Модуль підказує, що прочитати далі. Підказка має бути:

- **релевантною** історії користувача;
- **дозволеною** його роллю;
- **перевіреною і чинною** — без зразків ін'єкцій і замінених регламентів;
- **поясненою** — кожна рекомендація має шлях у графі знань, а не «чорну скриньку».

## Підходи (`reco/models.py`)

Усі моделі будують профіль користувача з журналу взаємодій. Кожна взаємодія має вагу: view = 1, cite = 3. Ваги згасають з періодом напіврозпаду 21 день.

1. **Популярність (baseline).** Сума зважених взаємодій усіх користувачів за фрагментом.
2. **Графовий (шляхи).** Від кожного переглянутого фрагмента (сіда) рахуються шляхи до кандидатів:
   - довжини 1 — через NEXT_SECTION;
   - довжини 2 — `I→E→I` (спільна сутність) і `I→D→I` (той самий документ);
   - довжини 3 — `I→G→G→I` (ребро графа знань, наприклад твердження → наратив).

   Вклад шляху дорівнює `вага сіда × вага типу / ступінь проміжного вузла`, тож рідкісні сутності важать більше. Ваги типів: MENTIONS 1,0; NEXT_SECTION 0,8; IN_DOC 0,6; KG 0,5. Для кожного кандидата зберігається найкращий шлях — він стає основою пояснення. Еквівалентний запит Cypher до Neo4j ЛР9/ЛР14:
   ```cypher
   MATCH (u:User {id:$u})-[v:VIEWED]->(s:Chunk)-[:MENTIONS]->(e)<-[:MENTIONS]-(c:Chunk)
   WHERE NOT (u)-[:VIEWED]->(c) AND c.sensitivity IN $allowed AND c.status <> 'superseded'
   WITH c, e, sum(v.weight / COUNT { (e)<-[:MENTIONS]-(:Chunk) }) AS score
   RETURN c.id, score ORDER BY score DESC LIMIT 10
   ```
3. **Ембединги (kNN).** Профіль — зважене середнє векторів переглянутих фрагментів; кандидати впорядковуються за косинусом до профілю.
   - На ПК: `intfloat/multilingual-e5-small` (як у ЛР10), вектори в `data/item_vecs_e5.npy`.
   - У хмарі й для швидких повторів: LSA (TF-IDF символьних 3–5-грам + SVD-128).
4. **Гібрид.** Два режими:
   - **зважений** — `w_g·graph + w_e·emb + w_p·log(1+pop)`, бали нормалізовано min-max; ваги підбираються сіткою з кроком 0,1 на validation;
   - **RRF** — `Σ 1/(60 + ранг)` за трьома списками, без навчуваних параметрів.

   Параметр `new_slots` резервує місця в кінці топу для нових фрагментів без взаємодій (див. `docs/cold_start.md`).

## Фільтри якості й доступу

Фільтри застосовуються **до ранжування**, тож заборонене не потрапляє навіть у кандидати (`items.allowed`).

| Фільтр | Правило | Параметр API |
|---|---|---|
| RBAC | guest → public; analyst → +internal; admin → +restricted. Роль береться з реєстру користувачів, не з запиту | — |
| Перевіреність | без документів, позначених неперевіреними (`INT-SAMPLE-INJ` — зразок публікації з ін'єкцією для розбору) | `require_verified` (типово true) |
| Чинність | без `status = superseded` (регламент 2025 замінено регламентом 2026) | `current_only` (типово true) |
| Свіжість | дата документа ≤ N днів до 2026-11-07 | `fresh_days` |

Демонстрація (`reco/filters_demo.py` → `results/filters_demo.json`, інтерес — регламенти перевірки):

| Випадок | Каталог | Що змінилось у топ-5 |
|---|---|---|
| guest, усі фільтри | 488 (лише public) | лише публічні W19/W06 |
| analyst, усі фільтри | 497 (+internal) | з'являються INT-REG-2026, INT-RULES |
| admin, усі фільтри | 525 (+restricted) | той самий топ: досьє наративів не про регламенти |
| admin, без фільтра перевіреності | 527 | +2 фрагменти INT-SAMPLE-INJ у каталозі |
| admin, з заміненими | 527 | на 1-му місці замінений INT-REG-2025 — саме тому фільтр увімкнено за замовчуванням |
| analyst, свіжість ≤ 60 днів | 107 | лише документи жовтня (INT-RULES, W19) |

У демонстраторі те саме перевіряє крок «+ Фільтр свіжості», а гість із заявленою роллю admin отримує лише public (крок 4b).

## Дані взаємодій (`reco/data_gen.py`)

Реальних журналів Hub немає, тому дані синтетичні; персональні дані не використовуються.

- 60 користувачів: 4 admin, 42 analyst, 14 guest.
- Кожен має 1–3 теми з 9 (Діріхле α = 0,6) і Пуассонову кількість сесій.
- Сесія — 1–4 послідовні фрагменти документа теми; 15 % сесій — «дослідження» за Zipf-популярністю.
- Документ доступний лише після своєї дати і лише дозволеній ролі.
- Події: view (85 %) або cite (15 %); seed 16 дає 2188 подій.
- Генератор не знає ні сутностей, ні ембедингів — лише теми документів.

## Обмеження

1. **Синтетичні взаємодії.** Абсолютні значення метрик не переносяться на реальних користувачів. Генератор читає розділи послідовно, що підіграє ребру NEXT_SECTION у графовому методі, а відбір за темами підіграє онбордингу за темами. Порівняння методів між собою чесне лише в межах цієї моделі поведінки.
2. **Покриття графа.** 37 % фрагментів (196) не мають жодної сутності. Газетир шукає назви за основою слова, тож можливі пропуски відмінкових форм і хибні збіги (наприклад, «Google» з'єднує тексти про дипфейки й тролінг).
3. **Малий каталог і мало користувачів.** 529 фрагментів і 50–53 користувачів у test дають широкі довірчі інтервали (±0,04–0,05 nDCG). Різниця між двома гібридами статистично не значуща (парний тест, `results/paired_e5.json`).
4. **Холодний старт документа.** Популярність у RRF «топить» нові фрагменти, тож потрібні примусові слоти. Їхня точність (hit@10) низька, а експозиція — помірна.
5. **Фільтр перевіреності грубий.** Позначка ставиться на рівні документа, а не твердження. Сумнівний фрагмент усередині перевіреного документа пройде.
6. **Ризик бульбашки.** Гібрид із популярністю знижує новизну (8,6 проти 9,7 біт в ембедингів e5). Для аналітиків, яким потрібні нові наративи, варто додати диверсифікацію (MMR) — це в планах.
